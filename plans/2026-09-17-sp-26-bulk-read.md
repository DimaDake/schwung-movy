# SP-26 — bulk read for a delegated page

**Item:** the delegated page reads ONE key per tick where movy's own refresh read
a whole page in one round trip. SP-13 measured it: ~1.25 blocking single-key
engine GETs per tick (Schwung's staggered cursor at 1/tick + `reloadIfChanged` at
2 per 8 ticks) at ~3.4 ms each — the +4.3 ms that takes the device tick from
4.9 ms to 9.1 ms. The tick period IS movy's MIDI sampling interval, so this is
the swallowed-detent complaint in its own units.

**Not this item:** quiescing the idle poll once every cell has been read (SP-13's
follow-on). If a gap remains after the measurement, it gets its own id.

## Design

movy owns the `io` object it hands Schwung's controller (`schwung-page-io.ts`),
so `io.getParam` can be served from a cache that a paced `port.getMany()`
prefetch fills.

- **`src/renderer/schwung-page-cache.ts` (new).** An epoch cache in front of one
  `TrackPort`. Every `FILL_TICKS` (8, the divider `reloadIfChanged` already uses
  and Schwung's own host paces its round trips on) the epoch advances and ONE
  `port.getMany()` refills every tracked key. A `get` in the current epoch is a
  map read; a miss is a single live read whose answer is cached for the rest of
  the epoch, so every key costs at most one round trip per epoch either way.
- **The tracked set is LEARNED, not predicted.** The keys asked in the last two
  epochs are the batch. Predicting from `ctl.page.keys` would have to re-derive
  Schwung's `fullKey` template resolution for child levels — a second
  implementation of the thing this migration exists to remove — and would still
  miss `:base`, `:effective`, `preset_name`, `ui_hierarchy` and `chain_params`.
  Learning covers all of them and self-corrects on a page change; the price is
  one rotation of live reads on arrival at a new page, which is exactly what
  today costs on every rotation.
- **Freshness is not lost.** Today the cursor re-reads a given cell once per
  rotation (~10 ticks for an 8-knob page). The cache refreshes every tracked key
  every 8 ticks. What does get coarser is a `live`/modulated key's `:effective`,
  which Schwung re-reads every tick: it now moves on the 8-tick fill (~25 Hz at
  a 5 ms tick), which is at the display's own cadence.
- **Bulky values stay out of the batch.** `SHADOW_PARAM_VALUE_LEN` is 128 KB for
  the whole bulk response and the fleet's biggest contract (minijv) is 85 KB of
  `ui_hierarchy` + `chain_params`. A response that overflows makes
  `paramGetMany` fall back to N single reads — correct, and exactly today's
  cost — so a key whose last value exceeded 16 KB is read live instead of
  batched. Everything else (plaits: 2.3 KB for both) rides the batch.
- **A batch-null is never cached.** `paramGetMany` maps `''` to `null`, so a
  bulk answer cannot tell "served and empty" from "read did not complete" — the
  tri-state Schwung's controller decides three different things on. An absent
  batch answer falls through to a live read, which is faithful, and THAT is
  cached.

## The stale-write hazard, and how it is prevented

SP-13 names it: do not serve a stale value while a write is in flight. On a
delegated page movy is the writer — the knob under the user's hand (through
`io.setParam`), the sequencer, automation (`app/tick.ts`), undo
(`undo/apply.ts`), the drum handler — and every one of those goes through the
SAME memoized `portFor(track)` instance.

So invalidation is **pull-based, at the port**: `EnginePort` logs the key of
every write with a sequence number (`writeSeq()` / `writesSince(seq)`), and the
cache drains that log before it serves ANY value. One mechanism covers every
writer, including the io's own `setParam`, with no listener to leak when
`schwungGridReload()` drops a page. A write to `k` drops `k` and `k:*` (`:base`,
`:effective`); a write to `<ck>:module` drops everything, because a module swap
changes every value on the page. A log overflow (more writes than the ring
holds between two reads) also drops everything — the safe direction.

## Tests (cheapest level that reproduces, teeth on each)

1. `browser-test/logic/schwung-page.mjs` — the SP-12 read-budget test, re-stated
   in ROUND TRIPS: a settled page must stay under one round trip per two ticks.
   Tooth: `FILL_TICKS = 1`.
2. Same file, the hazard: warm the cache, write a param through the port, and
   the controller's very next read must see the new value. Tooth: remove the
   drain in `get()`.
3. Same file: a value that changes behind movy's back is picked up within one
   fill — the cache must not be a freeze.
4. `browser-test/logic/page-owner.mjs` — structural: `schwung-page-io.ts` reads
   only through the cache (no direct `port.getParam`).
5. `browser-test/grid-cost.mjs` — the page arm's idle ROUND TRIPS per 600 ticks
   gets a ceiling, derived from the measured spread the way SP-13 derived 64.

`browser-test/env.mjs` gains `shadow_get_params`/`shadow_set_params` over the
real wire format: without them `paramGetMany` takes its per-key fallback, so the
off-device instrument counted params READ and was structurally unable to see a
round trip collapse — the exact thing this item changes. Both counts are
published: `calls` (params, SP-13's units, the existing gesture-premium gate) and
`trips` (round trips, the new one).

## Measurement

Re-run both instruments exactly as SP-13 did. Before (2026-09-16): device idle
period 4.89–5.00 ms (`off`) vs 9.11–9.48 ms (`page`), `ipc_ms` 1.22–1.45 vs
6.44–6.54; off-device idle 678 / 753, premium −418 / +43. Prediction to falsify:
~1.25 round trips/tick → ~0.1, i.e. +4.3 ms → ~+0.35 ms.

## Outcome (2026-09-17)

Closed. Device: tick period 9.11–9.48 → **6.80–7.20 ms** (`off` 4.80–5.00),
`ipc_ms` 6.44–6.54 → **1.5–1.9** (`off` 1.1–1.4), `calls/tick` 3.0 → 0.8. The
read premium is **+0.4 ms** against the ~+0.35 predicted — the prediction held.
Off device, idle round trips **753 → 146** (`off` 78).

Two things this plan did not foresee:

1. **A null must never be cached.** Caching a no-answer alongside a real one
   grew the burn-down 6 → 7 — a module that arrived while the grid was off
   screen read as having no hierarchy and the controller paginated
   `chain_params` into one page. `""` is a real answer and is cached; `null` is
   the channel declining to answer and is not. A re-plan drops the cache for the
   same reason: the cache ages in page ticks, and a page is ticked only while
   the grid is on screen.
2. **~1.9 ms of the gap is CPU, not IPC** (`tick_ms` 4.0–4.5 against 1.7–2.0).
   Recorded as **SP-27** rather than folded in, and it is NOT SP-13's quiescing
   follow-on — the reads are already down to ~0.1 a tick.

Ceilings derived from the measured spread, not rounded: logic budget 54 trips
over 64 ticks (measured 36), grid-cost idle floor 219 trips over 600 (measured
146), gesture premium 163 calls (measured 109).
